# Подготовка содержания для Almanac

Этот документ описывает редакционную и техническую работу над одной главой. Общая задумка — в `CONCEPT.md`, задания и критерии приёмки для будущего агента — в `CODEX_SPEC.md`.

## Текущий формат

Каноническое описание главы — JSON в `content/works/`. Текущая версия схемы: `schemaVersion: 1`. Формальная проверка находится в `content/schema/work.schema.json` и сборщике `tools/build.py`.

Сейчас наполнены три демонстрационные главы. Формат также допускает реальную работу без известного года, графиков или программы: `year: null`, пустые коллекции, `experiment.type: "none"`. Для такой работы не нужно придумывать значения, изображения или алгоритм, чтобы заполнить интерфейс.

`status` принимает `demo`, `draft`, `reviewed`. Происхождение материала — `demo`, `original`, `derived`, `reconstructed`. `draft` и `reviewed` — состояния редакционной подготовки главы, а не её приватности и не завершённости исторического исследования. В публичном репозитории черновой JSON и связанные файлы также публичны.

`templates/work.json.example` — минимальный шаблон заполнения. Он намеренно не участвует в сборке: год неизвестен, коллекции пусты, обложка отсутствует, эксперимента нет. Перед добавлением нового JSON следует заменить поясняющие строки подтверждённым содержанием и пройти валидацию. Связанные файлы создаются по необходимости.

## Поля главы

| Поле | Содержание | Правило |
| --- | --- | --- |
| `schemaVersion` | Версия формата | Сейчас `1` |
| `id` | Постоянный идентификатор главы | Латиница, цифры и дефис; сохранять после публикации |
| `title` | Название | Короткое и узнаваемое |
| `subtitle` | Поясняющий подзаголовок | Задача или предмет работы |
| `kind` | Вид работы | Например, диплом или прикладная программа |
| `year` | Год для хронологии | В demo условный; для архива подтверждённое число либо `null` |
| `status` | Состояние содержания | `demo`, `draft`, `reviewed`; не путать с завершённостью исторической работы |
| `summary` | Краткое описание | Несколько предложений без выдуманного авторства и результатов |
| `tags` | Темы | Небольшой список для поиска |
| `cover` | Путь к изображению | Относительно корня репозитория; пустая строка при отсутствии обложки |
| `sections` | Рассказ о работе | Разделы с `id`, `title`, `paragraphs`, необязательной `formula` |
| `figures` | Иллюстрации | Путь, заголовок, подпись, альтернативное описание и происхождение |
| `charts` | Числовые графики | Подписанные оси, серии пар `[x,y]`, примечание, происхождение |
| `code` | Просмотр исходников | Язык, путь, примечание и диапазоны строк с пояснением |
| `sources` | Материалы для скачивания | Название, путь, MIME-тип, пояснение, происхождение |
| `experiment` | Подготовленная лаборатория | `bch`, `trains`, `sensitivity` или `none`; пояснение обязательно |
| `methodNotes` | Ограничения и методические заметки | Краткие, конкретные, относящиеся к этой работе |

`code[].text` формируется сборщиком из указанного файла. Вручную в исходном JSON это поле не добавляется. Изменение файла кода должно сопровождаться проверкой диапазонов `highlights`.

Файл для встроенного просмотра кода должен быть в UTF-8 и занимать не более 1 000 000 байт. Для большого проекта выделите отдельный файл с содержательным фрагментом; полный оригинал сохраняется отдельно.

`provenance: "original"` означает неизменённый исходный материал; `derived` — извлечение, преобразование или новое представление на его основе; `reconstructed` — восстановленную реализацию или материал с описанием способа восстановления; `demo` — новый учебный пример. Одного такого ярлыка недостаточно для прослеживаемости: в `note`/`caption` и рабочем досье указываются конкретные основания и преобразования.

Все отображаемые строковые поля содержат обычный текст. HTML, скрипты и обработчики событий из содержания не выполняются. Строка формулы в текущем каркасе — текстовое представление; сложную формулу нельзя превращать в нечитаемую последовательность символов. Для таких формул потребуется отдельное локальное отображение и обязательная сверка с оригиналом.

## Порядок разбора реального архива

### 1. Инвентаризация

Работайте с копией архива вне публикуемого дерева. Для каждого файла запишите относительный путь внутри архива, размер, SHA-256, предполагаемый формат, состояние чтения и предполагаемую принадлежность к работе. Исходные даты файлов фиксируйте как метаданные, а не как установленный год создания.

Архивы распаковываются с проверкой путей. Нельзя допускать выхода файла за назначенную папку распаковки. Не запускайте содержащиеся в архиве EXE, макросы, скрипты установки и неизвестные бинарные программы только для выяснения их назначения. Сначала исследуйте документы, текстовые исходники и зависимости.

Обнаруженные копии сопоставляются по содержимому. Одинаковые имена не означают одинаковую версию, а одинаковый хеш подтверждает побайтовую копию. Если порядок версий не установлен, сохраните обе и запишите вопрос.

Используйте `templates/source-dossier.md`. Заполненное рабочее досье может содержать личные сведения, поэтому его место по умолчанию — рядом с входным архивом вне публичного репозитория.

### 2. Извлечение и понимание

**Word:** извлеките основной текст, таблицы, рисунки, подписи, сноски, формулы, приложения и библиографию. Сверяйте существенные фрагменты по визуально открываемому оригиналу или его проверенному рендеру. Объекты формул, плавающие рисунки и таблицы не следует считать успешно перенесёнными только потому, что извлёкся основной текст.

**Pascal и Delphi:** установите кодировку и сохраните оригинальные байты. UTF-8-копию для чтения создавайте отдельно. Просмотрите проектный файл, модули, формы, include-файлы, ресурсы и данные. По `.dfm` и обработчикам событий восстановите связь ввода с расчётом; учтите возможность бинарного формата формы. Если конвертация формы недоступна, укажите это в досье.

**Числовые данные:** установите смысл столбцов, единицы, десятичный разделитель, пропуски, кодировку и принадлежность конкретному сценарию. Значения не следует автоматически нормализовать так, чтобы исчезли особенности исходного расчёта.

Для БЧХ дополнительно выясните представление поля, примитивный и порождающий полиномы, направление битов и коэффициентов, индексацию, параметры кода, порядок выдачи синдромов, алгоритм коррекции. Для ТЭО выясните базу цен, период расчёта, состав затрат, единицы, дисконтирование, момент платежей и правила округления.

### 3. Смысловая карта

По каждой работе составьте короткую карту:

- Какую задачу она решает.
- Какие материалы подтверждают её название, дату и авторство.
- В чём состоит алгоритм или модель.
- Какие результаты сохранились и как они получены.
- Какая часть реализации или исследования не завершена.
- Какие сведения являются предположениями.
- Какие вопросы требуют воспоминаний владельца.

Не пытайтесь сделать все главы одинаковыми. Общая структура помогает ориентироваться, но содержание определяет глубину формул, количество рисунков и уместность эксперимента.

### 4. Рассказ для читателя

Предпочтительная последовательность: задача → идея решения → устройство модели → результаты → ограничения → связь с кодом и материалами.

Первый экран главы должен объяснять её тему человеку, не знакомому с проектом. Подробные формулы и листинги доступны дальше. Используйте конкретные понятия и примеры; не добавляйте биографические сцены, эмоции, историческую значимость или заявления о научной новизне без основания.

Современное объяснение пишется своими словами и с опорой на источники. В досье укажите точный фрагмент-основание: раздел и страницу документа, файл и диапазон строк, лист и ячейки таблицы. Для восстановленного текста отметьте, где понадобилась интерпретация.

### 5. Изображения и формулы

Сохраняйте оригинальную иллюстрацию, если её можно распространять. Производная версия получает отдельное имя и описание преобразования: обрезка полей, повышение читаемости, перерисовка схемы, восстановление формулы.

Перерисовка схемы проверяется по связям и обозначениям. Изменение расположения блоков не даёт основания изменять смысл стрелок. Формула проверяется по индексам, степеням, знакам, скобкам и единицам; догадки отмечаются до публикации.

`caption` объясняет, что показывает изображение и откуда оно взято. `alt` описывает значимую информацию изображения, чтобы его смысл был доступен без картинки. SVG используются для точных схем, растровые форматы — для сканов, фотографий и снимков интерфейса. Внешние изображения и исполняемый SVG-контент не должны становиться скрытой зависимостью автономной главы.

### 6. Графики

У каждого графика должны быть:

- Заголовок с понятным вопросом или показателем.
- Названия осей с единицами измерения.
- Названия серий и единый смысл каждой пары `[x,y]`.
- Исходные значения в доступной таблице или CSV.
- Основание: исходная таблица, вывод программы, новый расчёт или учебные значения.
- Существенные предположения и диапазон применимости.

Если значения считаны с картинки, отметьте приближённость и способ оцифровки. Новую скорость работы JavaScript нельзя представлять как исторический замер Pascal/Delphi. Не создавайте якобы измеренные данные, чтобы заполнить экран. Когда таблица утрачена, можно сохранить изображение исходного графика без выдуманного интерактивного аналога.

Статический график и CSV описывают явно названный базовый сценарий. Если интерактивный пример меняет значения, читатель должен понимать, к какому сценарию относится каждая таблица или экспорт.

В текущем формате координаты — конечные числа; внутри каждой серии `x` должен строго возрастать. Если исходные данные имеют повторные измерения или другой порядок, сохраните оригинал и явно опишите подготовку отдельного ряда для графика.

### 7. Исходники и браузерный пример

Выделяйте короткие содержательные процедуры и добавляйте объяснение их роли. Полный подготовленный исходник можно приложить отдельно. Кодировка, форматирование, переносы строк и номера строк должны быть согласованы с отображаемым файлом.

В браузер переносится вычислительное ядро, которое можно проверить. Текст из просмотрщика не исполняется через `eval`, `Function` или внедрение в DOM. Список лабораторий и допустимые типы определяются приложением. Для нового алгоритма создаётся отдельный понятный модуль с контролем входов и длительности расчёта.

Для перевода Pascal/Delphi выясните разрядность чисел, знаковость, переполнения, индексацию массивов, целочисленное деление, порядок битовых операций, точность и округление. В JavaScript битовые операторы работают с 32-битными значениями; для более широких кодовых слов потребуется явное представление, например массивы или `BigInt`, с проверкой границ.

Сверка включает исходные входы, промежуточные величины и итог. Если оригинал не удалось запустить, честно укажите основу новой реализации: описание метода, сохранённые таблицы, ручной расчёт. Такой результат не получает статус полной программной эквивалентности.

Эксперимент нужен только там, где он помогает понять работу. Отсутствие восстановимого алгоритма не должно мешать публикации достоверной текстовой главы.

## Подготовка и проверка готовых файлов

В корне репозитория:

```sh
python3 tools/build.py --validate
python3 tools/build.py
python3 tools/build.py --check
```

Первая команда проверяет исходное содержание, вторая обновляет браузерные данные и статические главы, третья выявляет расхождение исходников с сохранёнными результатами сборки. Дополнительные команды проверок смотрите в `package.json` и `README.md`; инструменты нужны автору, а не читателю.

Проверьте `index.html` через `file://`, страницу чтения, картинки, числа и скачиваемые файлы. На узком экране график и код могут иметь собственную прокрутку, но вся страница не должна выходить за ширину. Важно проверить фактические переходы и вычисления, а не только отсутствие сообщений об ошибках.

Завершение импорта оформляется по `templates/import-report.md`: что добавлено, что подтверждено, как проверено, что ещё неизвестно и что исключено из распространяемого издания. Не включайте в отчёт для публичного репозитория личные пути и сведения из рабочего досье.
